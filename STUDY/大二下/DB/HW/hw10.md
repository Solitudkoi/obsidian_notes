15.2
Consider the bank database of Figure 15.14, where the primary keys are underlined, and the following SQL query:
select T.branch name 
from branch T, branch S
where T.assets > S.assets and S.branch city = “Brooklyn”

Write an efficient relational-algebra expression that is equivalent to this query. Justify your choice.



**答案：**

π_{T.branch_name}(branch as T ⋈_{T.assets > S.assets} (σ_{branch_city='Brooklyn'}(branch as S)))

**Justification：**

这个表达式高效的原因在于**先做选择再做连接（selection pushdown）**。

σ_{branch_city='Brooklyn'} 先作用在 branch 上，过滤出只有 Brooklyn 的分支，得到一个很小的临时关系 S。然后这个小表 S 再和完整的 branch 表（作为 T）做 theta-join。

相比之下，如果先做笛卡尔积再过滤（即 σ_{T.assets > S.assets ∧ S.branch_city='Brooklyn'}(branch × branch)），需要先生成 branch 表和自身的完整笛卡尔积，元组数是 n² 级别，代价巨大。

把选择下推之后，参与 join 的 S 表可能只有几条记录，join 的代价从 O(n²) 降到 O(n × k)，其中 k 是 Brooklyn 分支的数量，远小于 n。

此外，如果 branch_city 上有索引（如 B+ 树），σ_{branch_city='Brooklyn'} 可以用索引快速完成，进一步减少代价。


**Expression:**

π_{T.branch_name}(branch as T ⋈_{T.assets > S.assets} σ_{branch_city='Brooklyn'}(branch as S))

**Justification:**

This expression is efficient because it applies selection before the join. By first filtering branch with σ_{branch_city='Brooklyn'} to get a small relation S, the subsequent theta-join only needs to compare each tuple in T with the few Brooklyn branches in S, rather than computing a full Cartesian product of branch with itself. This reduces the join cost from O(n²) to O(n × k), where k is the number of Brooklyn branches.

### 15.19: Variant of Hybrid Merge-Join

Both r₁ and r₂ are **not physically sorted**, but both have a **sorted secondary B+-tree index** on the join attribute C.

**Algorithm:**

1. Merge the leaf entries of the two B+-tree indices on C. Since both indices are sorted on C, this is a standard merge. The result is a list of pairs (rid₁, rid₂) — pointers to matching tuples in r₁ and r₂.
    
2. Sort the result pairs by the physical address of r₁ tuples.
    
3. Scan r₁ in physical order, and for each matching entry, retrieve the corresponding r₁ tuple. Append the associated r₂ pointer to it.
    
4. Sort the result by the physical address of r₂ tuples.
    
5. Scan r₂ in physical order, retrieve the matching r₂ tuples, and produce the final join output.
    

This avoids sorting the actual relations — we only merge the (much smaller) index leaf levels and sort pointer lists.

### 15.20: Cost Estimation

Given: b₁ = 800, b₂ = 1500.

Let b_{i1} and b_{i2} be the number of leaf-level blocks of the B+-tree indices on r₁ and r₂. Since index entries are much smaller than data tuples, typically b_{i} ≪ b_{r}. However, the problem doesn't give exact index sizes, so we express costs in terms of b_{i1} and b_{i2}.

**Step 1: Merge the two index leaf levels**

- Block transfers: b_{i1} + b_{i2}
- Seeks: ⌈b_{i1}/b_b⌉ + ⌈b_{i2}/b_b⌉

**Step 2: Sort result pairs by r₁ address**

Let b_p be the number of blocks occupied by the result pairs.

- Block transfers: b_p × (2⌈log_{M-1}(b_p/M)⌉ + 1)
- Seeks: 2⌈b_p/M⌉ + b_p × (2⌈log_{M-1}(b_p/M)⌉ - 1)

**Step 3: Scan r₁ in physical order**

In the worst case each matching tuple is in a different block, but scanning in physical order means sequential access:

- Block transfers: b₁ = 800 (at most, full scan of r₁)
- Seeks: 1 (sequential scan)

**Step 4: Sort result by r₂ address**

Same as Step 2 cost (sorting the intermediate result).

**Step 5: Scan r₂ in physical order**

- Block transfers: b₂ = 1500 (at most, full scan of r₂)
- Seeks: 1 (sequential scan)

**Total:**

- Block transfers = (b_{i1} + b_{i2}) + 2 × b_p(2⌈log_{M-1}(b_p/M)⌉ + 1) + b₁ + b₂
- Seeks = ⌈b_{i1}/b_b⌉ + ⌈b_{i2}/b_b⌉ + 2 × [2⌈b_p/M⌉ + b_p(2⌈log_{M-1}(b_p/M)⌉ - 1)] + 2

The key advantage over a plain merge join is that we **never sort the actual data files** (which are 800 and 1500 blocks). We only merge the smaller index files and sort pointer pairs, then do two sequential scans of the data files.

### 15.6

Given: A B+-tree index on `branch_city` is available on relation `branch`. No other index is available.

**(a) σ_{¬(branch_city < "Brooklyn")}(branch)**

This is equivalent to **branch_city ≥ "Brooklyn"**.

Use the B+-tree index to find the first entry with branch_city ≥ "Brooklyn", then follow the leaf-level pointers to retrieve all subsequent entries sequentially. This avoids a full table scan.

**(b) σ_{¬(branch_city = "Brooklyn")}(branch)**

This is equivalent to **branch_city ≠ "Brooklyn"**.

**Method 1**: Use a linear scan of the entire branch file, discarding tuples where branch_city = "Brooklyn".

**Method 2**: Use the index to do two range scans — one for branch_city < "Brooklyn" and one for branch_city > "Brooklyn".

Since ≠ typically matches most records, the linear scan (Method 1) is usually more efficient. The index-based approach would incur many random I/Os, especially if it is a secondary index.

**(c) σ_{¬(branch_city < "Brooklyn" ∨ assets < 5000)}(branch)**

By De Morgan's law: ¬(A ∨ B) = ¬A ∧ ¬B

This is equivalent to **branch_city ≥ "Brooklyn" AND assets ≥ 5000**.

Use the B+-tree index on branch_city to retrieve all records with branch_city ≥ "Brooklyn" (same as part (a)). Then test each retrieved record in memory against the condition assets ≥ 5000, since no index is available on assets.

### 15.20

Given (from 15.3): b₁ = 800, b₂ = 1500, b_b = 1.

The question asks to estimate the cost of **merge join** for r₁ ⋈ r₂.

**If r₁ and r₂ are not already sorted:**

Sorting cost for each relation:

- Block transfers: T_Sort(r_i) = b_{r_i} × (2⌈log_{M-1}(b_{r_i}/M)⌉ + 1)
- Seeks: S_Sort(r_i) = 2⌈b_{r_i}/M⌉ + b_{r_i} × (2⌈log_{M-1}(b_{r_i}/M)⌉ - 1)

Merge phase cost:

- Block transfers: b_{r₁} + b_{r₂} = 800 + 1500 = 2300
- Seeks: b_{r₁} + b_{r₂} = 2300

Total:

- Block transfers = T_Sort(r₁) + T_Sort(r₂) + b_{r₁} + b_{r₂}
- Seeks = S_Sort(r₁) + S_Sort(r₂) + b_{r₁} + b_{r₂}

**If r₁ and r₂ are already sorted:**

- Block transfers = b_{r₁} + b_{r₂} = 800 + 1500 = **2,300**
- Seeks = b_{r₁} + b_{r₂} = **2,300**
