## 第一部分：Lecture 9 — 索引与散列 (Indexing and Hashing)

### 1. 为什么需要索引？

想象你在图书馆找一本书。没有目录就得一本一本翻，有了目录就能直接定位。数据库索引的原理一样——通过维护一个小得多的"目录文件"（索引文件），加速对数据记录的查找。

索引文件里的每条记录叫**索引项 (index entry)**，格式是 `(search-key, pointer)`，其中 search-key 是用来查找的属性值，pointer 指向对应的数据记录。

### 2. 两大类索引

**顺序索引 (Ordered Index)**：索引项按 search-key 值排序存储。适合范围查询（如 `WHERE salary BETWEEN 50000 AND 80000`）。

**散列索引 (Hash Index)**：用散列函数把 search-key 映射到桶(bucket)。适合等值查询（`WHERE id = 123`），但不适合范围查询。

### 3. 顺序索引的细分

**聚集索引 (Clustering/Primary Index)**：索引的排序顺序和数据文件本身的物理排列顺序一致。一个数据文件最多只能有一个聚集索引。

**非聚集索引 (Secondary Index)**：索引的排列顺序与数据文件的物理顺序不同。可以有多个。

**稠密索引 (Dense Index)**：数据文件中每一个 search-key 值都有一条索引项。查找快但占空间。

**稀疏索引 (Sparse Index)**：只为部分 search-key 值建索引项（通常每个数据块一条）。省空间但查找要多走几步。只能用于聚集索引（数据有序才行）。

**多级索引 (Multilevel Index)**：当索引文件本身也太大放不进内存时，对索引再建一层稀疏索引，可以层层嵌套。

### 4. ⭐ B+ 树 — 这是重点中的重点

B+ 树是数据库最常用的索引结构，解决了普通索引文件需要定期重组的问题。

**核心性质（n 是一个节点能容纳的指针数）**：

- 所有叶子节点在同一层（平衡树）
- 非根非叶节点有 ⌈n/2⌉ 到 n 个子节点
- 叶子节点有 ⌈(n-1)/2⌉ 到 n-1 个 search-key 值
- 根如果不是叶子，至少有 2 个子节点
- 叶子节点之间通过指针串成链表，方便顺序扫描

**节点结构**：`P₁ K₁ P₂ K₂ ... K_{n-1} Pₙ`

**叶节点**：Pᵢ 指向 search-key = Kᵢ 的数据记录，Pₙ 指向下一个叶子节点。

**非叶节点（内部节点）**：

- P₁ 指向的子树中所有值 < K₁
- Pᵢ 指向的子树中所有值 ≥ Kᵢ₋₁ 且 < Kᵢ
- Pₙ 指向的子树中所有值 ≥ Kₙ₋₁

### 5. B+ 树的插入操作

1. 找到目标叶节点
2. 如果叶节点有空间，直接插入
3. 如果叶节点满了，**分裂 (split)**：
    - 把 n 个键值对（包括新的）排好序，前 ⌈n/2⌉ 留在原节点，其余放到新节点
    - 新节点中最小的 key 值**上提**到父节点
4. 如果父节点也满了，继续分裂，向上传播
5. 最坏情况：根节点也分裂，树高度 +1

**内部节点分裂**（与叶节点不同）：中间的 key 值 K_{⌈n/2⌉} 上提到父节点，**不保留在任何子节点中**。

### 6. B+ 树的删除操作

1. 找到并删除目标叶节点中的键值
2. 如果节点键值数仍 ≥ ⌈(n-1)/2⌉，完成
3. 否则节点**太少 (underflow)**：
    - 如果兄弟节点有富余，**借 (redistribute)**：从兄弟借一个键值过来，更新父节点
    - 如果兄弟也刚好够用，**合并 (merge)**：把两个节点合并成一个，删除父节点中对应的键值
4. 合并可能导致父节点也 underflow，向上传播
5. 如果根节点只剩一个子指针，删除根，子节点成为新根，树高度 -1

### 7. 聚集索引 vs 辅助索引的区别（14.17题的答案）

这正好是你作业的一道题：

- **聚集索引**：search-key 顺序 = 数据文件物理排列顺序。顺序扫描高效，可以用稀疏索引。
- **辅助索引**：search-key 顺序 ≠ 数据文件物理顺序。必须是稠密索引，顺序扫描代价高（每条记录可能需要一次磁盘 I/O）。

## 第二部分：Lecture 10 — 查询处理 (Query Processing)

### 1. 代价度量

数据库的查询代价主要看磁盘 I/O：

- **块传输 (block transfer)**：读/写一个磁盘块，耗时 tT ≈ 0.1ms
- **磁盘寻道 (seek)**：磁头定位，耗时 tS ≈ 4ms

总代价 = b × tT + S × tS（b 是块传输次数，S 是寻道次数）

### 2. 选择操作的算法

- **A1 线性扫描**：逐块扫描，代价 = bᵣ 次传输 + 1 次寻道
- **A2 二分查找**：要求数据有序且连续存储，代价 = ⌈log₂(bᵣ)⌉ 次传输和寻道
- **A3 主索引等值查找（键属性）**：代价 = (hᵢ + 1) × (tT + tS)，hᵢ 是索引树高
- **A4 主索引等值查找（非键属性）**：hᵢ × (tT + tS) + tS + b × tT
- **A5 辅助索引等值查找**：键属性同 A3；非键属性代价 = (hᵢ + n) × (tT + tS)，可能很贵

### 3. ⭐ 连接操作 — 重点

**嵌套循环连接 (Nested-Loop Join)**：

```
for each tuple tᵣ in r:
    for each tuple tₛ in s:
        if (tᵣ, tₛ) 满足条件，输出
```

最坏代价：nᵣ × bₛ + bᵣ 次块传输，nᵣ + bᵣ 次寻道

**块嵌套循环连接 (Block Nested-Loop Join)**：

```
for each block Bᵣ of r:
    for each block Bₛ of s:
        对 Bᵣ 和 Bₛ 中所有元组配对检查
```

最坏代价：bᵣ × bₛ + bᵣ 次块传输，2 × bᵣ 次寻道

改进版（内存有 M 块时）：外层关系用 M-2 块，代价降为 ⌈bᵣ/(M-2)⌉ × bₛ + bᵣ 次块传输

**索引嵌套循环连接**：外层每条元组用内层关系的索引查找，代价 = bᵣ × (tT + tS) + nᵣ × c

**归并连接 (Merge Join)**：两个关系都按连接属性排序后归并，代价 = bᵣ + bₛ（加排序代价）

**散列连接 (Hash Join)**：用散列函数把两个关系分区，同分区的元组才需要比较，代价 = 3(bᵣ + bₛ)

### 4. 外排序 (External Sort-Merge)

当关系大到放不进内存时使用：

1. **生成归并段**：每次读 M 块到内存，排序后写回磁盘，产生 ⌈bᵣ/M⌉ 个归并段
2. **多路归并**：每次合并 M-1 个段
3. 总共需要 ⌈log_{M-1}(bᵣ/M)⌉ 趟归并
4. 块传输总代价：bᵣ × (2⌈log_{M-1}(bᵣ/M)⌉ + 1)

### 15.2：SQL 查询的关系代数表达式和执行方案

题目：

```sql
SELECT T.branch_name 
FROM branch T, branch S
WHERE T.assets > S.assets AND S.branch_city = 'Brooklyn'
```

这个查询的含义是：找出所有资产(assets)大于某个布鲁克林分支的分支名称。

等价的关系代数表达式有多种写法：

**表达式 1**（先选择再连接）： π_{T.branch_name}(σ_{T.assets > S.assets}(branch as T ⋈ σ_{branch_city='Brooklyn'}(branch as S)))

**表达式 2**（先做笛卡尔积再全选）： π_{T.branch_name}(σ_{T.assets > S.assets ∧ S.branch_city='Brooklyn'}(branch as T × branch as S))

执行策略：先用选择条件 `branch_city='Brooklyn'` 过滤出布鲁克林的分支（得到小表S），再与 branch 表（作为T）做 theta-join（条件是 `T.assets > S.assets`），最后投影出 `T.branch_name`。如果有 `branch_city` 上的索引，可以用它加速选择操作。

### 15.3：连接代价估算

已知：r₁ 有 20,000 条元组，r₂ 有 45,000 条元组；25 条 r₁ 放一个块，30 条 r₂ 放一个块。

先算块数：

- b₁ = 20000/25 = **800 块**
- b₂ = 45000/30 = **1500 块**

**(a) Nested-loop join（嵌套循环连接）**

用 r₁ 做外层关系（元组少）更好。

最坏情况（内存只够放一个外层块 + 一个内层块）：

块传输 = n₁ × b₂ + b₁ = 20000 × 1500 + 800 = **30,000,800**

寻道 = n₁ + b₁ = 20000 + 800 = **20,800**

如果反过来用 r₂ 做外层：块传输 = 45000 × 800 + 1500 = 36,001,500（更差）

所以选 r₁ 做外层。

**(b) Block nested-loop join（块嵌套循环连接）**

最坏情况（内存 M=3 块）：

用 r₁ 做外层（块数少）：

块传输 = b₁ × b₂ + b₁ = 800 × 1500 + 800 = **1,200,800**

寻道 = 2 × b₁ = 2 × 800 = **1,600**

用 r₂ 做外层则：1500 × 800 + 1500 = 1,201,500（稍差）

所以选 r₁ 做外层。

### 15.6：带否定的选择操作处理

假设 `branch_city` 上有 B+ 树索引。

**(a) σ_{¬(branch_city < "Brooklyn")}(branch)**

即 `branch_city ≥ "Brooklyn"`。可以用 B+ 树索引：查找第一个 `branch_city ≥ "Brooklyn"` 的索引项，然后顺序扫描到末尾。

**(b) σ_{¬(branch_city = "Brooklyn")}(branch)**

即 `branch_city ≠ "Brooklyn"`。有两种方法：一种是线性扫描全表，跳过 `branch_city = "Brooklyn"` 的记录。另一种是用索引分两段扫描：先扫 `branch_city < "Brooklyn"` 的部分，再扫 `branch_city > "Brooklyn"` 的部分。如果布鲁克林的记录很少，线性扫描反而更简单。

**(c) σ_{¬(branch_city < "Brooklyn" ∨ assets < 5000)}(branch)**

由德摩根律：¬(A ∨ B) = ¬A ∧ ¬B，所以等价于 `branch_city ≥ "Brooklyn" AND assets ≥ 5000`。

可以用 B+ 树索引找到 `branch_city ≥ "Brooklyn"` 的所有记录，然后在内存中逐条检查 `assets ≥ 5000`。

### 15.20：基于 15.19 的连接代价估算

题目说要用 15.19 的解法来估算 r₁ ⋈ r₂ 的代价。15.19 通常是要求设计一个基于归并连接 (merge-join) 的策略。

b₁ = 800，b₂ = 1500。

**Merge-join 的代价**：

归并连接需要先排序两个关系。假设内存大小为 M 块。

排序 r₁ 的块传输代价：b₁ × (2⌈log_{M-1}(b₁/M)⌉ + 1) 排序 r₂ 的块传输代价：b₂ × (2⌈log_{M-1}(b₂/M)⌉ + 1) 归并阶段的块传输：b₁ + b₂

如果假设 M 足够大能一趟归并（例如 M ≈ 25 或更大），排序 r₁：⌈800/25⌉ = 32 个初始归并段，需要 ⌈log₂₄(32)⌉ = 2 趟归并，块传输 = 800 × (2×2 + 1) = 4000。排序 r₂：⌈1500/25⌉ = 60 个段，⌈log₂₄(60)⌉ = 2 趟，块传输 = 1500 × 5 = 7500。归并：800 + 1500 = 2300。

总块传输 ≈ 4000 + 7500 + 2300 = **13,800**（远优于块嵌套循环的 120 万）

寻道需要另外计算（取决于 buffer 分配策略），大约为 2 × ⌈800/M⌉ + 2 × ⌈1500/M⌉ 加上归并阶段的寻道。
