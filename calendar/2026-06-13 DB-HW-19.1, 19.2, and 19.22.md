# 一、考试最重要的知识点

## 1. Recovery 的目标

数据库故障后仍然保证 ACID 中的：

- **Atomicity（原子性）**
    
    - 事务要么全部完成，要么全部撤销
        
- **Durability（持久性）**
    
    - 已提交事务不能丢失
        

为此引入：

- Log（日志）
    
- Undo（撤销）
    
- Redo（重做）
    
- Checkpoint（检查点）
    

---

## 2. Undo 与 Redo

### Undo

恢复到修改前状态。

日志记录：

```text
<Ti, X, old_value, new_value>
```

Undo 时：

```text
X ← old_value
```

用途：

- 事务未提交就崩溃
    
- 事务主动 Abort
    

---

### Redo

恢复到修改后状态。

Redo 时：

```text
X ← new_value
```

用途：

- 已提交事务的数据还没来得及写回磁盘就崩溃
    

---

## 3. WAL（Write Ahead Logging）

这是最爱考的概念。

规则：

> Log must be written before data.

即：

```text
先写日志
后写数据库页
```

这样即使系统崩溃，也能根据日志恢复。

课件明确称为：

> Write-Ahead Logging (WAL) Rule。

---

## 4. Checkpoint

Checkpoint 的作用：

- 不必从日志开头恢复
    
- 缩短恢复时间
    

执行 Checkpoint 时：

1. 刷新日志
    
2. 将修改过的缓冲区写盘
    
3. 写入
    

```text
<checkpoint L>
```

其中 L 是当前活跃事务集合。

恢复时：

只需从最近 checkpoint 开始处理。

---

## 5. ARIES

考试知道思想即可：

三阶段：

### Analysis

找：

- 哪些事务没完成
    
- 哪些页是 dirty page
    

---

### Redo

Repeat History

即：

```text
把历史重新执行一遍
```

---

### Undo

撤销未完成事务。

---

# HW 19.1

题目：

> Explain why log records for transactions on the undo-list must be processed in reverse order, whereas redo is performed in a forward direction.

---

## 答案

Undo 必须按逆序执行，因为事务回滚时需要按照与原更新相反的顺序撤销修改。

假设：

```text
T1:
A = 10 → 20
A = 20 → 30
```

日志：

```text
L1: <A,10,20>
L2: <A,20,30>
```

若回滚：

必须先撤销 L2：

```text
30 → 20
```

再撤销 L1：

```text
20 → 10
```

否则若先撤销 L1：

```text
30 → 10
```

再撤销 L2：

```text
10 → 20
```

最终结果错误。

因此 Undo 需要从最新日志向前扫描（backward scan）。

---

Redo 则必须按正序执行，因为恢复时要重新按照事务原来的执行顺序重放操作。

例如：

```text
A: 10 → 20
A: 20 → 30
```

Redo：

```text
10 → 20
20 → 30
```

最终得到正确结果 30。

如果逆序：

```text
10 → 30
再执行旧操作
```

可能产生错误状态。

因此：

- Undo → backward scan
    
- Redo → forward scan
    

这是恢复算法正确性的保证。

# HW 19.2

题目：

> Explain the purpose of the checkpoint mechanism...

---

## （1）Checkpoint 的目的

Checkpoint 的目的是：

### 减少恢复时需要扫描的日志量

系统崩溃后：

不需要从日志开头恢复，

只需要从最近 checkpoint 开始恢复。

因此：

```text
减少恢复时间
```

---

## （2）Checkpoint 应该多久执行一次？

没有固定答案。

需要在：

```text
Checkpoint 开销
vs
恢复速度
```

之间权衡。

通常：

- 周期性执行
    
- 或日志达到一定大小执行
    

---

## （3）Checkpoint 频率对正常运行性能的影响

Checkpoint 越频繁：

- 更多磁盘 I/O
    
- 更多日志刷盘
    
- 更多缓冲区写回
    

因此：

```text
正常运行性能下降
```

Checkpoint 越少：

```text
正常运行性能更好
```

---

## （4）Checkpoint 频率对系统崩溃恢复时间的影响

Checkpoint 越频繁：

恢复时需要扫描的日志更少。

因此：

```text
恢复更快
```

Checkpoint 越少：

```text
恢复更慢
```

---

## （5）Checkpoint 频率对磁盘故障恢复时间的影响

媒体故障（disk failure）恢复过程：

```text
最近一次数据库备份（dump）
+
之后的日志重做
```

Checkpoint 不会改变备份时间点。

因此：

### 影响很小

恢复时间主要取决于：

- 最近 dump 距离现在多久
    
- 需要 redo 的日志量
    

而不是 checkpoint 频率。

---

# HW 19.22

题目：

> Suppose there is a transaction that has been running for a very long time but has performed very few updates.

---

## (a) 对恢复时间有什么影响？

### 普通恢复算法（Section 19.4）

影响较大。

原因：

Checkpoint 中会记录活跃事务：

```text
<checkpoint L>
```

这个长事务始终处于 active 状态。

恢复时：

系统必须一直向前或向后扫描日志，

直到找到该事务的：

```text
<T start>
```

记录。

即使它只更新了很少数据，

仍可能导致：

```text
扫描大量日志
```

恢复时间变长。

---

### ARIES

影响较小。

ARIES 使用：

- Dirty Page Table
    
- RecLSN
    
- LastLSN
    
- CLR
    

只需处理与该事务真正相关的日志记录。

因为该事务更新很少：

```text
Undo 工作量很小
```

因此恢复时间增加有限。

虽然 Analysis 阶段仍需跟踪该事务，

但远小于传统算法的影响。

---

## (b) 对删除旧日志记录有什么影响？

影响很大。

日志能否删除取决于：

```text
是否还可能用于恢复
```

对于长时间运行事务：

```text
<T start>
```

可能非常早。

系统必须保留从该 start 开始到现在的相关日志。

否则：

如果该事务失败，

无法执行 Undo。

因此：

### 长事务会阻止旧日志被删除

导致：

- 日志文件增长
    
- 占用更多存储空间
    

无论是传统恢复算法还是 ARIES，都必须保留恢复所需日志。

# 19.1

### Explain why log records for transactions on the undo-list must be processed in reverse order, whereas redo is performed in a forward direction.

**Answer:**

Undo operations must be performed in reverse order because the effects of a transaction must be removed in the opposite order in which they were originally executed. The most recent update must be undone first to correctly restore the database to its previous state.

For example, if a transaction updates a data item from 10 to 20 and later from 20 to 30, the system must first undo the second update (30 → 20) and then the first update (20 → 10). Processing undo records in any other order may lead to an incorrect final value.

Redo operations, on the other hand, must be performed in the forward direction because they repeat the original sequence of updates. Replaying the updates in the same order ensures that the database reaches the exact state that existed before the crash.

Therefore, undo is performed backward to reverse the effects of a transaction, while redo is performed forward to reproduce its effects.

# 19.2

### Explain the purpose of the checkpoint mechanism. How often should checkpoints be performed? How does the frequency of checkpoints affect:

### • System performance when no failure occurs?

### • The time it takes to recover from a system crash?

### • The time it takes to recover from a media (disk) failure?

**Answer:**

The purpose of the checkpoint mechanism is to reduce recovery time after a failure. A checkpoint records a consistent state of the database and identifies active transactions, allowing recovery to start from the most recent checkpoint instead of scanning the entire log.

There is no fixed interval for performing checkpoints. They should be performed periodically, balancing normal system performance and recovery efficiency.

**Effect on system performance when no failure occurs:**

Frequent checkpoints increase overhead because log records and modified pages must be written to stable storage more often. As a result, normal transaction processing may become slower.

**Effect on recovery time after a system crash:**

Frequent checkpoints reduce recovery time because fewer log records need to be scanned and processed during recovery. Infrequent checkpoints result in longer recovery times.

**Effect on recovery time after a media (disk) failure:**

Checkpoint frequency has little direct effect on media-failure recovery. Recovery from a disk failure mainly depends on restoring the latest database dump (backup) and redoing committed transactions recorded in the log after the dump. Therefore, backup frequency is more important than checkpoint frequency for media-failure recovery.

# 19.22

### Suppose there is a transaction that has been running for a very long time but has performed very few updates.

### (a) What effect would the transaction have on recovery time with the recovery algorithm of Section 19.4, and with the ARIES recovery algorithm?

**Answer:**

With the recovery algorithm of Section 19.4, a long-running transaction can significantly increase recovery time. Since the transaction remains active across multiple checkpoints, the recovery process may need to scan much further back in the log to locate its start record, even if the transaction performed only a few updates.

With ARIES, the impact is much smaller. ARIES uses structures such as the Dirty Page Table, RecLSN, and transaction-specific log chains to limit the amount of log processing required. Because the transaction has performed very few updates, the amount of undo work is small, and recovery remains relatively efficient.

---

### (b) What effect would the transaction have on deletion of old log records?

**Answer:**

A long-running transaction delays the deletion of old log records. The system must retain all log records that may be needed to undo the transaction if it later aborts or if recovery is required after a crash.

As a result, log records generated since the transaction started cannot be safely removed. Therefore, a very long-running transaction can cause the log to grow larger and prevent old log records from being deleted until the transaction completes.
